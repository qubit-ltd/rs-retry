## 方案选择

选择局部测试加固和文档修正。替代方案一是仅给 CI 作业增加整体 timeout，成本低但不能定位具体测试，且失败时间过长；替代方案二是重做 worker 执行协议或引入通用测试框架，没有生产缺陷证据且超出收益范围。两者均不采用。

### RSRETRY-001：让测试在回归时及时失败

证据定位：

- `tests/executor/worker_retry_tests.rs`：`test_worker_timeout_uses_injected_timer`；`test_worker_retry_matches_shared_infrastructure_and_timeout_matrix` 的 timeout 分支；`test_worker_timeout_poll_failure_reaps_operation`。
- `tests/executor/worker_contract_tests.rs`：`test_worker_attempt_timeout_has_a_distinct_terminal_reason`、`test_worker_shorter_flow_timeout_reports_flow_source`。

这些用例直接或间接依赖被测取消信号结束 worker 循环；注入计时器用例还在时钟推进后无界 join。手动时间已推进不等于唤醒与取消传递完成，`cancellation_grace` 也不能覆盖尚未识别停止事件的等待。

采用两层、仅供测试使用的保护：

1. **worker 侧独立退出**：循环使用标准 `Instant`，正常检测尝试取消；真实时间 5 秒仍未取消时设置独立 `AtomicBool` 并返回。该标记不能依赖手动时钟或取消传播，且测试在原有终止原因断言外必须断言标记为 false。不要只在 worker 内 panic，因为 panic 可能被 worker 执行器捕获后掩盖。
2. **测试控制侧有界等待**：将上述用例主体放入测试 runner 线程，通过结果 channel 在总计 10 秒内接收结果，包含断言 panic 的传播。只在 `JoinHandle::is_finished()` 成立后 join；确认线程结束的轮询也受同一个真实截止时间约束。不得在超时错误分支无条件 join。

共享代码放入新的测试辅助文件 `tests/support/worker_watchdog.rs`，通过 `tests/support/mod.rs` 在 `worker` feature 下导出。它只提供有界运行和取消等待两个小 helper，不形成生产 API、通用线程池或新的执行框架。五个用例复用 helper，避免各自遗漏保护分支。

正常路径继续通过显式 started/deadline 事件协调并推进手动时钟，不新增固定 sleep 作为同步手段，不以真实时间判断生产 timeout 是否正确。5/10 秒只用于检测测试失去进展；正常通过不需要等满期限。

异常路径在 5 秒内让合作测试 worker 退出，外层总期限限制测试线程等待。若出现超出本轮假设的执行器深层死锁，外层报告失败并丢弃未结束的 JoinHandle，不能强杀 Rust 线程，也不能宣称已回收所有异常线程。此时实施者应报告新证据；不要顺手修改生产线程协议。测试 worker 正常路径和可恢复的注入故障路径应完成退出。

验收：原有终止原因、尝试数与手动耗时断言保持；watchdog 未触发。临时让一个测试 worker 观察独立的永不取消 token 时，测试应在保护期限内失败且不误通过；恢复故障注入后通过。

### RSRETRY-002：保护正常决策的短路行为

修改 `tests/rule/rule_order_contract_tests.rs::test_first_rule_wins_and_failure_kind_is_stable`。第二条 `AbortRule` 持有 `Arc<AtomicUsize>`，在 `decide` 中递增计数；运行后额外断言计数为 0，保留原有 `Exhausted { Attempts }` 和最后失败分类断言。测试专用 helper type 可以继续留在用例内。

不修改生产规则选择逻辑。验收应证明后续规则没有被调用，而不只是最终决策仍取首条规则。为校准计数，单独让同一个计数规则作为首条规则执行一次，确认计数为 1；这也能避免计数器接错对象导致假通过。

### RSRETRY-003：保护一次性映射闭包

修改两个已有用例：

- `tests/error/attempt_failure_tests.rs::test_map_error_consumes_application_error_once`。
- `tests/error/retry_error_tests.rs::test_map_error_preserves_context_and_completion_diagnostics`。

在 `error.push_str(&suffix)` 后消费捕获的 `String`：`drop(suffix)`，再返回 `error`。闭包因此只实现 `FnOnce`；若 API 错误收紧为 `Fn`/`FnMut`，用例不能编译。保留非 Clone 业务错误、映射结果、上下文和完成诊断的现有断言，复用 timeout/panic 不调用 mapper 的现有测试。

无需新增 trybuild 依赖、compile-fail fixture 或修改映射 API。代码通过类型检查本身就是一次性闭包兼容性的验收证据，不将“当前测试本就应该通过”伪造成修复前运行失败。

### RSRETRY-005：补足 Session 调度接入边界

在英文指南 `Let your scheduler own the wait` 与中文指南 `让现有调度器负责等待` 中，既有示例之后补充等义但自然组织的说明：

- 只有 `Admitted` 才能执行操作；一次准入恰好对应一次 `record_result`。
- 活动期间重复 `begin_attempt`、未准入或重复 `record_result`、终态后继续调用属于状态误用，会 panic，而非返回 RetryError。
- `Waiting` 不产生新操作，不应调用 `record_result`；`Complete`、`Failed` 或准入返回 Err 后停止使用该 Session。
- Session 使用构造后的 `.with_cancellation_token(token)`；其他执行器的 `.cancellation_token(token)` 不能直接套用。
- 取消在准入与失败控制边界检查，不能打断已准入操作，也不会自行唤醒外部调度器；调度器负责响应信号并再次驱动 Session。不得把“调用 cancel”写成即刻关闭正在执行的操作。

复用两种语言的现有完整示例，加入 `RetryCancellationToken` 导入和 `.with_cancellation_token(token)` 绑定；令牌在正常路径保持未取消，原有等待/完成断言保留。取消的可运行入口可在同一个 `main` 中用第二个预取消 Session 演示 `begin_attempt` 返回取消错误以及零次准入；所有代码仍在原有 `kind=run features=none deps=clock-test-util` 标注内。无需新增库功能、额外文档或与当前目标无关的状态图。
